一、结构（对照交接说明 [验收] 项）
1. 引擎共享与借用：PlaceholderEngine 挂在 AicliRuntime 的 PrivacyGate 上
   （Arc<RwLock<…>>，懒构造一次），StreamRestorer 改为 EngineSource
   （Borrowed/Shared）——'static 的 SSE 流持有 Arc，push/finish 内短读锁
   （restore 只读），不跨 .await、不在流生命周期内持锁。并发测试
   （只挂隐私中间件的 mini app）：SSE 流挂着时另一请求 5s 内完成遮盖
   （masked_values 增加）
2. 引擎只构造一次：首次使用时 from_store 读一次钥匙串；失败置
   engine_failed，按模式处理，不反复重试（C4-03 教训）
3. 设置缓存：PrivacyGate 内 (修订号, 快照)；aicli_set_privacy 提交后
   bump 全局修订号（静态原子量，命令与代理无需同一运行时实例），
   热路径修订号未变不读库
4. 层顺序：.layer(privacy) 写在 local_auth 之前（axum 后加在外层 →
   鉴权先执行）。测试固定：错误令牌请求 401 且 bodies_read 计数不变
   （隐私层未读 body）、上游零捕获

二、行为（对照清单条款）
- 隐私关闭：直接 next.run(req)，不读 body（计数断言）；关闭时上游
  body 与重复请求逐字节相同；开启但正文无敏感值时也逐字节相同
- AI 路径 POST（messages/chat/completions/responses/generateContent
  系列/app/alpha/search）；图片生成与编辑接口：block → 400
  privacy_media_unsupported，pass → 放行计数
- 请求：读 body → Content-Encoding 解压并移除头 → mask_json →
  content-length 重建 + Accept-Encoding: identity；不支持编码/非 UTF-8
  按模式处理
- 含 data:/file_data 媒体：block 且未放行 → 422 privacy_media_blocked
  （错误信息说明如何放行）；放行时文本照遮、data: 原样（E-04 keepIn）
  并计数
- 响应：SSE → RestoreStream 包装（RestoreStream/finish、panic 处理）；
  其他整体 restore_json（含错误响应）；上游压缩流式：block → 502
  privacy_compressed_stream（fail-closed），pass → 原样透传
- 引擎异常：mask/restore_json 在 catch_unwind 内（AssertUnwindSafe，
  中毒锁 into_inner）；故障注入（test-hooks）3 位置 × 2 模式全过：
  block → privacy_engine_failed / 流立即结束（不透传后续字节）；
  pass → 原文放行 / 占位符透传，均计数降级
- 日志：只记数量（masked_values/degraded/media_passed/bodies_read），
  捕获 logger 断言不含敏感值；PlaceholderEngine/Held/StreamRestorer
  无 Debug

八、验收打回修正（2026-11-08，第三轮）
1. 流式 panic 恢复改为 **restorer 内部逐事件 catch_unwind**（修正第二轮
   「注入在 push 之前」的局限）：
   - StreamRestorer.push 全程字节（Vec<u8>）：本次 push 中已还原的事件
     照常输出；出错事件、之前被扣留的事件（Held.raw）与 buf 剩余字节
     按原始字节放出；restorer 置 passthrough（后续 push 原样返回）+ 
     failed 粘滞标志。不再有「已处理事件随局部变量丢失」「当前块重复」
     「from_utf8(chunk).unwrap_or("") 丢块」「lossy 产生 U+FFFD」的问题
     （多字节跨块的字节留在 buf，不经任何有损转换）
   - 注入点挪到事件还原内部（set_stream_fault_event(N)，restorer 计
     事件数；FAULT_STREAM 上膛才生效，默认第一个事件）
   - RestoreStream 不再外层 catch：push 后按 restorer.engine_failed()
     处理——block：先发已还原部分再返回 Err 断流（计数一次）；pass：
     restorer 已透传，字节照走
   - e2e stream_fault_mid_event_keeps_restored_prefix_and_raw_suffix：
     一个块内含完整事件（emoji 文本）+ 出错事件 + 下一事件开头，块边界
     切在 😀 与中文字节中间；断言客户端收到的字节 = 已还原事件 + 其后
     上游原始字节（逐字节相等）、无 U+FFFD、degraded=1。原有 pass/block
     第 N 块两测改用事件级注入，帧完整断言不变
2. PrivacyGate::refresh 出错语义修正：出错时**本次按 fail-closed（开启 +
   block）处理，不更新缓存修订号**（修正第二轮「保留快照到新修订号」会
   把关闭固化的问题）；下次请求自动重试；持续出错按 1s 最短重试间隔
   限频（期间仍 fail-closed）。单元测试
   refresh_error_fails_closed_and_recovers：缓存关闭 → 开启（bump）→
   DROP 表出错 → settings()=开启+block；重建表后 bump → 返回真实设置；
   再改 pass → 跟随真实值

十、全链路并发复核（2026-11-08，统一验收）

响应体排队）」经复核**不成立**：
- 原诊断未入库；当时的 mock 由全局 UpstreamMode 决定回什么。并发诊断
  用的 SseHeld 模式下，第二个请求同样拿到「首块后挂起、等 release」
  的 SSE，响应头已到而响应体要等 release——这正是记录里「上游往返已
  完成、卡在 bytes_with_limit 直到前一个流结束」的现象。代码排查也没有
  跨请求的锁：代理到上游走 HTTP/1（direct_client 连接池 / hyper 原始
  连接，各请求独立连接），response_processor 的异步锁是每个流各自的
  事件收集器
